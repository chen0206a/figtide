# FigTide 桌面版迁移指南（MySQL 网页版 → 桌面版）

把网页版（MySQL，`scripts/start.ps1` 启动）里保存的项目迁移到桌面版（内嵌 H2 文件库，
`java -jar figtide.jar --spring.profiles.active=desktop`）。迁移是**复制**：工具对旧版只
调用 `GET /api/projects` 和 `GET /api/projects/{p}/backup`，全程不写旧库；桌面版出现的是
同名新项目，旧版数据原样保留。

## 1. 迁移前

- **建议先手动备份**：在旧版网页里对每个重要项目用「项目备份」导出一份 zip，自己存好。
  迁移工具本身也会把每个项目的导出 zip 存进报告目录（见第 4 节），但多一份自己掌握的
  备份更稳妥。
- 确认磁盘空间足够：桌面数据目录（`%LOCALAPPDATA%\FigTide\data`）要容纳全部项目数据，
  报告目录还要再存一份备份 zip。
- 迁移期间不要在旧版里改数据（新增图表、上传数据集等），避免两边对不上。

## 2. 启动两边的服务

1. 旧版照常启动：

   ```powershell
   .\scripts\start.ps1 -SkipBuild   # 首次或代码更新后不要加 -SkipBuild
   ```

   健康检查：<http://127.0.0.1:8086/api/health>。

2. 桌面版启动（需要先构建一次桌面 jar：`.\scripts\build-desktop.ps1`）：

   ```powershell
   & "$env:JAVA_HOME\bin\java.exe" -jar .runtime\desktop-build\figtide.jar --spring.profiles.active=desktop
   ```

   双击安装包运行同理。注意托盘或浏览器地址栏里的端口（默认首选 17861；被占用时本次会
   随机换端口并弹气泡提示）。桌面版数据在 `%LOCALAPPDATA%\FigTide\data`。

3. 两个服务都活着即可开始；工具检查两端地址不同且To是桌面版。From应填写你已启动的旧版地址；工具仅访问旧端项目列表和项目备份，不探测额外接口来判断源数据库类型。

## 3. 先做 DryRun（不写入任何数据）

```powershell
.\scripts\migrate-to-desktop.ps1 -From http://127.0.0.1:8086 -To http://127.0.0.1:17861 -DryRun
```

DryRun 只做两件事：把每个项目的备份导出到报告目录（留作离线副本）、在桌面版上做恢复
预检查（解析、校验、大小上限）。查看报告目录里的 `migration-report.md`：

- 所有项目都是「干跑」→ 正常，可以正式迁移；
- 有「跳过：过大」→ 该项目备份超过桌面版上限（512 MiB 压缩 / 768 MiB 展开），见下方
  「已知限制」；
- 有「失败」→ 按报告里的报错排查，先解决问题再继续。

## 4. 正式迁移

```powershell
.\scripts\migrate-to-desktop.ps1 -From http://127.0.0.1:8086 -To http://127.0.0.1:17861
```

每个项目的处理：

- 导出旧版备份 → 报告目录保存编号副本（`001-项目名.labflow.zip`，名字做了文件名安全
  处理）；
- 在桌面版恢复成**同名新项目**，然后重新导出并与旧版导出逐字段规范化比对，内容一致才
  记「成功」；有任何差异记「失败」并列出差异；
- 桌面版已有同名项目时：内容一致 → 记「已迁移」（跳过，重复运行安全）；内容不一致 →
  恢复为「原名（迁移）」；较长名称会为后缀预留空间，保持在120字以内。合法的同名图表和同名模板会全部保留；
- 源项目是归档状态 → 恢复后通过项目更新接口把归档状态补回去。

结束后看汇总与报告（`migration-report.md` / `.json`）：

| 结果 | 含义 |
| --- | --- |
| 成功 | 已恢复并通过内容比对 |
| 已迁移 | 之前已迁移过，内容一致，本次跳过 |
| 跳过：过大 | 备份超过桌面版上限，未恢复（备份 zip 已在报告目录） |
| 失败 | 恢复或比对出错，报告里有具体差异/报错；非零退出码 |

命令退出码非 0 表示有失败项——按报告处理，不需要从头再来（其余项目已经完成）。

## 5. 迁移后验证

- 在桌面版浏览器里逐个打开项目，检查图表、数据集、实验列表与旧版一致；
- 归档项目在项目列表里应显示归档标记；
- 迁移报告里每个项目都有一张旧/新计数对照表（数据集数 / 数据版本数 / 图表数 /
  图表版本数 / 实验数 / 实验数据链接数 / 样式模板数），两边应完全一致。

## 保留旧版本

**迁移完成后不要立刻删除或清空旧版数据。**旧版（`.runtime/mysql/` 数据目录）继续可用
作为回退；建议至少保留到你已经在桌面版上稳定使用一段时间之后。旧版停止：

```powershell
.\scripts\stop.ps1   # 保留数据
```

## 已知限制

- **助手的运行记录和会话不随迁移保留**：备份格式（`labflow-project-v1`）本来就不包含
  `agent_runs` / `agent_sessions`，这是桌面方案既定范围。迁移报告的结尾也会注明这一点。
- **超过上限的项目**：桌面版单项目备份上限为 512 MiB（压缩）/ 768 MiB（展开），默认网
  页版导出上限是 64 MiB / 96 MiB，因此正常能从旧版导出的项目都能迁过去；报告里的
  「跳过：过大」意味着该项目连旧版自己的导出上限都超了，需要先在旧版里拆分或精简。
- 时间字段：迁移保留数据里的时间戳；「导出时刻」（报告 `started_at`）每次运行都不同，
  属于元信息，不影响内容比对（比对时已排除）。

## 故障排查

- **报告目录在哪？** 不加 `-Out` 时默认是 `.runtime\migration-<时间戳>\`；每行的第一屏
  输出和报告末尾都会写明路径。
- **想单独重迁某个失败的项目？** 报告目录里该项目的 `.labflow.zip` 是完整的项目备份，
  可以在桌面版网页里用「项目备份 → 恢复备份」把它恢复成新项目。
- **误把 From/To 写反了？** 目标必须能通过桌面版ping检查；填成旧版会被拒绝。源端始终只读，但仍应核对两端地址；工具不检查源数据库类型。
- **桌面版换端口了？** 用托盘气泡/浏览器地址栏确认实际端口再传 `-To`；端口被占时桌面
  版本次会临时随机换端口，重启后会回到首选端口。
- **中途断电/中断？** 旧库不受影响（全程只读）；桌面版上已恢复的项目在下次运行时会按
  同名比对决定跳过或续传，重新运行同一个命令即可。

## 自动化验收（开发者）

仓库里有完整的迁移 E2E（隔离 MySQL 测试库 + 临时目录桌面 jar，绝不触碰真实工作区）：

```powershell
.\scripts\test-migration.ps1
```

覆盖：代表性项目种子（多版本、ROC、混淆矩阵、派生数据、实验对比、归档、特殊字符、
≈51 MiB 大项目、同名图表/模板、120字名称冲突）→ 全部成功 → 二次运行幂等 → 改名副本复核成功 → 篡改检测（`--verify` 失败退出）→ 旧库
行数与 CHECKSUM 前后一致 → 浏览器渲染。证据样例见
`docs/test-evidence/desktop14-3-migration-*.json`。
