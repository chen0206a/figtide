# 任务 18 设计：多 agent 协作与「审稿」

**状态**：已确认，任务书见 tasks/18-agent-team.md。界面见设计画布「任务 18 · 多 agent 与审稿」一页。

## 1. 要解决什么问题

现在的绘图助手是单个 agent：理解一句话 → 调用绘图工具 → 生成提案。它能改样式和结构，但有两类事情做不好：
1. **跨领域的请求**：「按模型分组算 SEM，画成带区间带的折线，图例放右下」需要先做数据处理，再画图、调样式；单个 agent 在一次循环里容易漏步骤，或者直接在绘图层伪造误差。
2. **没人把关**：提案只保证「能通过校验」，不保证「符合期刊要求」。按 88 mm 成品算字号只有 5 pt、图例压住数据、误差线没说明是 SD 还是 SEM，这些问题现在都会原样交给用户。

## 2. 角色

| 角色 | 职责 | 可用工具 | 不能做 |
|---|---|---|---|
| **协调者** | 理解请求，拆成子任务，决定交给谁、按什么顺序；汇总各专家的结果，合并成一份提案 | 只读工具（字段摘要、图表规格、当前配置） | 直接修改图表 |
| **数据专家** | 处理类子任务：过滤、分组、汇总（mean / SD / SEM），生成派生数据集的处理规则 | 现有数据处理接口（只生成「处理规则提案」） | 修改原始数据；伪造误差列 |
| **绘图专家** | 样式和结构类子任务：图表类型、字段映射、序列、坐标轴、图例、画布 | 现有 10 个绘图工具（preview） | 保存 |
| **审稿专家** | 按检查清单审查**合并后的提案**，给出问题列表；能修的问题附带修复操作 | lint、检查清单、渲染事实（见第 4 节） | 修改数据；删除用户明确要求的内容 |

**不变的原则**：所有专家的产出合并成**一份提案、用户只确认一次**；共用同一个会话预算；不自动保存；原始数据只读；现有的提案校验、乐观锁、预算预留和结算、幂等、取消和超时、审计全部沿用。

## 3. 协作流程

```
用户请求
  └─ 协调者：拆分 → 计划（最多 4 个子任务）
       ├─ 数据专家（如果需要）→ 处理规则提案
       ├─ 绘图专家 → 绘图操作提案
       └─ 合并（处理规则 + 绘图操作）
            └─ 审稿专家 → 问题列表
                 ├─ 可自动修复且不违背用户原意的问题：修复操作并入提案，标注「审稿修复」
                 └─ 需要用户判断的问题：作为「审稿意见」列出，不自动修改
  └─ 一份提案：用户的修改 + 审稿修复（可逐条取消）+ 审稿意见
```

- **审稿最多一轮**：审稿修复之后只再跑一遍确定性检查，不让 LLM 来回改，避免循环烧预算。
- **冲突处理**：审稿专家的修复不能推翻用户在本轮请求里明确要求的内容（例如用户要求「图例放上方」，审稿不能挪到右侧，只能提出意见）。
- **审计**：每个专家的步骤、工具调用、token 用量单独记录，界面上可以展开查看。

## 4. 审稿检查清单

**先确定性、后 LLM**：能用规则判断的不交给模型，结果可复现、不花钱。

| # | 检查项 | 方法 | 可自动修复 |
|---|---|---|---|
| R1 | 按成品物理尺寸换算后的最小字号 ≥ 6 pt（可按期刊设置调整） | 规则：`publication` + 配置 | 是：调大字号 |
| R2 | 线宽 ≥ 0.5 pt | 规则 | 是 |
| R3 | 序列颜色在常见色觉缺陷下可区分 | 规则：模拟红绿色盲后计算颜色间距 | 是：换成色盲友好配色 |
| R4 | 颜色种类 ≤ 8，多于 8 时建议分面或合并 | 规则 | 否（意见） |
| R5 | 坐标轴有标题；物理量带单位 | 规则 + LLM 判断标题是否像物理量 | 否（意见，附建议文字） |
| R6 | 误差线 / 区间带说明了含义（SD / SEM / CI）和 n | 规则：配置中的统计口径 + 图注 | 部分：补图注 |
| R7 | 图例不遮挡数据 | **渲染事实**：前端从 Plotly 取图例和数据点的边界框，随请求一起发送 | 是：移动图例 |
| R8 | 文字不重叠、不出界 | 渲染事实：标题、刻度、注释的边界框 | 部分 |
| R9 | 对数轴、截断轴有明确标示 | 规则 | 否（意见） |
| R10 | 同一项目内相同指标的配色一致 | 规则：对比项目内其他图 | 否（意见） |

「渲染事实」只包含几何信息（边界框、颜色值、字号），不包含数据值，符合现有隐私说明。

## 5. 界面

1. **助手面板**：标题显示「绘图助手 · 协作中」；运行过程按专家分段显示进度（协调者 → 数据 → 绘图 → 审稿），每段可以展开看步骤。
2. **提案**分三组：「你要求的修改」「审稿修复」（默认勾选，可以逐条取消）「审稿意见」（不改图，只提示）。底部仍然只有一个「应用这组调整」。
3. **画布**：沿用现有的编号标记；审稿问题用另一种颜色的标记（橙色）标在问题位置。
4. **单独的「审稿这张图」**：编辑器顶栏新增按钮，只运行审稿专家（确定性检查不需要模型，没配置模型也能用；LLM 检查项需要配置模型并勾选同意）。

## 6. 评测（和多 agent 一起交付）

1. **任务集**（放在 `backend/src/test/resources/agent-eval/` 已有的评测框架里）：
   - 120 条改图请求，覆盖单步样式、多步结构、需要数据处理三类，每条有期望的配置变化；
   - 40 张「埋了问题」的图（每张埋 1–3 个 R1–R10 的问题），用来评测审稿。
2. **对比**：同一模型、同一预算上限，单 agent 与多 agent 各跑一遍：
   - 改图：配置完全符合期望的比例、多余改动率、工具调用次数、token、延迟；
   - 审稿：问题检出率（召回）、误报率（精确率）、修复后再检通过率。
3. **回放模式**：首轮用真实模型录制，之后用已有的回放机制复跑，CI 里不调用收费模型。
4. **报告**：`docs/AGENT-EVALUATION.md` 新增一节，给出两种模式的表格和置信区间（Bootstrap），如实写结论——如果多 agent 提升不明显，就写明，并保留「审稿」作为独立功能。

## 8. 关于 RAG 和期刊规范

审稿需要知道「目标期刊要求什么」。期刊对图的要求大多是**结构化的**（栏宽、最小字号、线宽、文件格式、配色建议），用一张规则表表示比检索文本更可靠、可复现。建议：
- 第一步：做一份「期刊图表要求」规则表（只收录作者指南里的数字要求和来源链接，不复制原文），作为 R1、R2 等检查项的参数来源；
- 只有当需要回答开放性问题（「这个期刊对误差线有什么要求？」）并给出原文出处时，才考虑在此基础上加 RAG。
