# 任务 14-3：从旧版（MySQL）迁移到桌面版

**先读**：`AGENTS.md`、`docs/development/desktop/DESKTOP-PLAN.md`（第 4、5 节）、`docs/desktop/DB-AUDIT-glm-5.3.md` 第 4 节（备份与恢复）。
**目标**：提供一个迁移工具，把旧版（MySQL）里的所有项目完整复制到桌面版（H2），并**自动核对**每个项目迁移前后完全一致，生成迁移报告。
**这一步风险最高**：迁移针对的是用户的真实研究数据。本任务**只在隔离的测试库上开发和验证**，不连接真实工作区（`labflow` 库 / 8086），也不碰用户的桌面数据目录。真实迁移由仓库主人按最后写好的说明自己执行。
**分支**：从 `desktop/14-2` 新建 `desktop/14-3`，每节单独提交，不推送。

---

## 14-3-0 设计原则（必须遵守）

1. **旧库只读**：只调用旧版的 `GET /api/projects` 和 `GET /api/projects/{p}/backup`（导出是只读事务），不对旧版发任何写请求。
2. **迁移是复制**：不删除、不修改旧库里的任何东西。
3. **复用现有备份格式**：通过旧版导出备份、再调用桌面版的 `POST /api/backups/restore` 恢复，不新写一套导入逻辑。
4. **每个项目都要核对**：核对不通过的项目，在报告里标为失败，并列出差异；工具最后以非零退出码结束。
5. **可重复运行**：同一个项目第二次运行时，如果桌面版里已经有内容完全一致的同名项目，就跳过，标为「已迁移」，不重复创建。

## 14-3-1 后端的少量配套修改

1. **备份大小上限可配置**：`BackupService` 里写死的压缩 64 MiB / 展开 96 MiB 上限，以及 multipart 上传上限，改为配置项。**默认值不变**；`desktop` profile 调大到压缩 512 MiB / 展开 768 MiB（本机使用，没有网络传输负担）。补测试：默认 profile 仍按原上限拒绝超大备份。
2. **恢复后保持原来的归档状态**：迁移工具恢复之后，如果原项目是归档的，就调用现有的项目更新接口设置 `archived=true`。不修改 `restore()` 的行为。
3. 以上都属于 AGENTS.md「桌面版后端授权」范围，汇报时注明。

## 14-3-2 迁移工具

新建 `scripts/migrate-to-desktop.ps1`（逻辑可以放在一个 Node 脚本里，ps1 只负责调用）：

```
./scripts/migrate-to-desktop.ps1 -From http://127.0.0.1:8086 -To http://127.0.0.1:17861 [-DryRun] [-Out <报告目录>]
```

流程：
1. 检查两端都在运行：旧版调用 `GET /api/projects`；桌面版调用 `GET /api/desktop/ping`，并确认对方确实是桌面版。`-From` 和 `-To` 指向同一个服务时，直接报错退出。
2. 列出旧版的所有项目（包括已归档的）。
3. 逐个项目：
   - 导出备份，保存到报告目录（这些备份文件本身就是一份完整的离线副本，迁移结束后保留）；
   - 预检查备份大小，超过桌面版上限的，标为「跳过：过大」，并给出处理建议；
   - `-DryRun` 模式下只导出和预检查，不恢复；
   - 恢复到桌面版，项目名沿用原名；如果桌面版已有同名项目，先按 14-3-3 的规则比较：完全一致就跳过，不一致就用「原名（迁移）」恢复；
   - 恢复原归档状态；
   - 按 14-3-3 核对。
4. 生成报告：`migration-report.json` 和一份给人看的 `migration-report.md`。每个项目一行：结果（成功 / 已迁移 / 失败 / 跳过）、数据集数、数据版本数、图表数、图表版本数、实验数、样式模板数，两边分别是多少；失败的列出具体差异。报告末尾写明：**助手的运行记录和会话不随迁移保留**（这是方案里定好的），以及旧库没有被修改过。

## 14-3-3 核对方法：往返比较

不要只比较数量。用「往返」的方式逐字段比较：
1. 旧版导出的备份清单 A；
2. 恢复到桌面版后，再从桌面版导出该项目，得到清单 B；
3. 两份清单规范化后必须完全一致。规范化规则：
   - 去掉所有数据库 ID，引用关系改用稳定的键表示（数据版本用「数据集名 + 版本号 + SHA-256」，图表用「图表名 + 版本号」，实验用「实验名 + 创建时间」）；
   - 图表配置里的 `datasetVersionId`、`source_meta_json` 里的各种 ID 引用，都按上面的稳定键替换后再比较；
   - 项目自身的 `created_at` 不比较（恢复时会变成当前时间，这是已知行为），其余时间字段要一致；
   - 原始文件比较 SHA-256，同时核对字节长度。
4. 规范化函数写成可单测的纯函数，单测覆盖：ID 不同但内容相同 → 一致；任意一个字段、一个原始文件字节、一条链接不同 → 不一致。

## 14-3-4 测试

1. **测试数据**：在隔离的 MySQL（8087 / `labflow_e2e`）上用接口造一组有代表性的项目：多个数据版本、派生数据集（处理结果，带 `source_meta`）、实验和实验-数据链接、多版本图表（包括 ROC、混淆矩阵这类专业图）、样式模板、一个已归档项目、一个含中文和特殊字符名称的项目，以及一份接近 64 MiB 的大备份。
2. **端到端**：启动临时数据目录的桌面版 jar，运行迁移工具，断言报告全部成功、退出码为 0；再运行一次，断言全部「已迁移」、桌面版没有新增项目；用浏览器打开桌面版，迁移过来的图表能正常渲染（复用现有 E2E 的打开图表步骤）。
3. **失败路径**：在测试中人为篡改桌面版的一条记录（只在测试库），再运行核对，断言报告标出失败和差异、退出码非零。
4. **旧库只读**：迁移前后对旧测试库各表做行数和校验和快照，断言完全不变。

## 14-3-5 给用户的迁移说明

新建 `docs/desktop/MIGRATION.md`（README 链接到它），写给普通用户看：
1. 迁移前：先用旧版的「项目备份」手动导出重要项目，作为额外保险；
2. 启动旧版（原来的脚本方式）和桌面版；
3. 先运行 `-DryRun`，看报告；
4. 正式运行，看报告，全部「成功」再继续；
5. 确认桌面版里数据都在之后，旧版可以保留一段时间再停用；
6. 已知限制：助手历史不迁移；超大项目的处理办法；
7. 出问题怎么办：报告目录里的备份文件可以随时在桌面版里单独恢复。
